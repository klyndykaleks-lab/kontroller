# STM32–ESP: отдельный транспорт, тестовая сборка v1

## Реализовано

USART1 обслуживается только задачей espLink (AboveNormal, MDB — High).
RX DMA: DMA2 stream 2/channel 4, кольцо 4096 байт. TX DMA: stream 7/channel 4.
Обе очереди — 16 строк по 128 байт; API постановки/получения не ждёт.
Обработка протокола, оплаты и моторов остаётся в managerTask.
MDB не ждёт передачи ESP; собственная передача MDB USART2 остаётся синхронной.
Задача espLink блокируется на один tick между проходами; busy-loop с taskYIELD нет.
DMA использует отдельный неизменяемый буфер до окончания передачи. При BUSY/таймауте
транспорт удерживает строку и повторяет её; ведущий LF отделяет частичный кадр.
Результаты и существующий outbox менеджера сохранены. Служебный reset после ACK
отложен до опустошения DMA-очереди либо до предела 1 секунда.
Диагностика старта: status=esp-async-v1. Таймаут оплаты STM32 — 60000 мс.
SD-защита сохраняет уже полученную команду до окончания транзакции FSM.

Интерфейс ESP и терминальный JSON не менялись. Перепрошивать ESP этим файлом нельзя.
Физические выводы и полярность MDB не менялись: USART2 PA3 RX / PA2 TX.
Документ AGENTS.md описывает старый software UART/30 s, фактический код — hardware/60 s.

## Что доказано программно

Запуск: `./scripts/test-controller.sh`. Компилируются настоящий esp_link.c с mock HAL/RTOS
и настоящий mdb.c. Отдельно проверяются извлечённые SD admission helpers.
T01–T03: available → denied → available без reset, устаревший результат предыдущего tx.
T04: отмена до оплаты; T05: таймаут/поздний ответ/переполнение tick.
T06–T07: отсутствие ACK, однократное подтверждение, VEND_FAILURE.
T08–T10: раннее завершение сессии, reset, OOS compatibility.
Транспорт: BUSY, timeout/retry, срок жизни DMA-буфера, очередь, фрагменты RX,
переполнение кольца, ошибка UART и восстановление границ строк.
Это проверки отдельных модулей. Они не исполняют полный managerTask/ESP/эквайринг
и не подтверждают реальные остатки, возврат, мотор или timing MDB на JL22.

## Подготовка стенда

Сохранить рабочие бинарники и конфигурацию. Записать версии всех трёх плат.
Залить только F411 в 0x08000000; не выполнять полный erase: boot identity в sectors 6/7.
Не переставлять известную рабочую распиновку кабеля.
Запись MDB: CH0 — машина, CH1 — контроллер, общая временная шкала, сохранить raw CSV/SAL.
Для корреляции ESP нужны ещё два канала на UART STM32↔ESP (115200 8N1).
Два MDB-канала сами по себе не показывают, когда ESP отправил результат.
Не подключать входы анализатора к питанию MDB. Подключать к согласованным по уровню
измерительным точкам. Изменение проводки — при снятом питании.

До и сразу после каждого теста:

```sh
curl --noproxy '*' --connect-timeout 2 --max-time 5 \
 'http://192.168.1.10:8000/network-settings' > status_before.json
# выполнить ровно один тест
curl --noproxy '*' --connect-timeout 2 --max-time 5 \
 'http://192.168.1.10:8000/network-settings' > status_after.json
```

Для каждого опыта отдельная папка, status до/после, raw capture, время действий,
выбранный товар/цена/остаток, фактическая выдача, списание и возврат по терминалу.
lastReason может сохранять старую причину; оценивать новые события и boot/tx/op.

## Последовательность на оборудовании (пока НЕ выполнена)

| Тест | Действия | Критерий |
|---|---|---|
| H00 | Холодный старт, ждать готовности | MDB инициализация, ESP видит F411, без циклов reset |
| H01 | Товар A с остатком → B с нулём → A, без перезапуска | B не списывает деньги и не выдаёт; обе покупки A завершаются, B не оставляет un_finished |
| H02 | Выбор → обычная оплата → кофе | Один платёж, одна выдача, сессия закрывается, следующая покупка доступна |
| H03 | Выбор → отмена до оплаты → новая покупка | Поздний ответ старого tx не разрешает новую выдачу |
| H04 | Выбор → не платить до timeout → новая покупка | Нет выдачи/повторного списания; контекст старого tx закрыт |
| H05 | Успешная оплата → ошибка выдачи | Финальный результат связан с исходным tx; банковский возврат подтверждён отдельно |
| H06 | Оплата товара с привязкой к мотору | Один запуск мотора, подтверждённое завершение; нет дополнительной выдачи кофе |

H01 выполнять первым после H00. При неуспехе остановить денежные тесты и сохранить
состояние до перезапуска, затем снимок старта. Сначала выяснить, на каком кадре расходится FSM.

После успешных H01–H06 повторить по одному разрыву за опыт (2–5 с):

| Точка разрыва | Что проверить после восстановления |
|---|---|
| До выбора | Без готового транспорта продажа не должна стать неподтверждённым списанием |
| После PAYMENT_REQUEST, до результата | Старый tx не оплачивает следующую покупку; timeout/отмена закрывают исходную |
| После банковского успеха, до получения результата STM32 | Сверить фактическое списание, выдачу и возврат; не повторять платёж вручную |
| После разрешения MDB, до VEND_SUCCESS/FAILURE | Одна выдача и один финальный исход при повторных сообщениях |
| После START мотора, до FINISH | Восстановление запрашивает состояние по прежнему boot/tx/op; повторного вращения нет |
| После FINISH, до получения результата ESP | Повтор/запрос возвращает прежний исход без нового START |

Проверять отдельно Wi-Fi, логический UART и связь с моторной платой: потеря Wi-Fi
не равна потере UART. Проводные разрывы выполнять заранее подготовленным безопасным
размыкателем сигнальной линии; питание/землю под нагрузкой не разрывать. Без такого
стенда сначала ограничиться отключением Wi-Fi. Не выдавать испытание Wi-Fi за UART/I2C.

## Границы текущего решения

UART TC означает выход битов из STM32, а не приём ESP. При отключённом проводе
UART/DMA может завершиться успешно. Гарантии доставки/возврата требуют прикладных
подтверждений, журналов и сверки на ESP/сервере. Очереди конечны; RX overflow теряет данные
с диагностическим счётчиком и ресинхронизацией. TX retry может повторить строку;
идемпотентность boot/tx/op обязательна. Транспорт не отменяет уже поставленный
PAYMENT_REQUEST при завершении сессии: задержанный запрос обязан быть безопасно
сопоставлен с отменой на ESP/сервере. Это отдельно проверить H03/H04 с разрывом.
Изоляция задач не исправляет сама по себе аппаратную полярность, конфликт периферии,
ошибку FSM или неверное состояние остатков. Срок ответа MDB измерить анализатором.
